### 6.1.1 צד לקוח – React ו-TypeScript

**הסבר.** אפליקציית עמוד יחיד (SPA) אחת, שמציגה מסלול ניווט שונה לכל תפקיד (איור 5.1). נתוני השרת מנוהלים ב-TanStack Query, הגרפים מוצגים ב-Recharts, ונתוני סטים שטרם נשלחו נשמרים ב-IndexedDB עד חידוש החיבור.

**נימוקים לבחירה**

1. **הפרדת הציור המהיר מעדכוני הממשק.** השלד מצויר על שכבת Canvas בקצב הפריימים, מחוץ למחזור הרינדור של React. מונה החזרות ופס המשוב מתעדכנים רק באירוע (חזרה או שגיאה), כך שהממשק אינו מאט את לולאת העיבוד (NFR-01).
2. **חוזה מוקלד עם השרת.** טיפוסי TypeScript נוצרים אוטומטית מסכמת ה-OpenAPI של השרת, ולכן שינוי במבנה נתוני הסט שובר את בניית הלקוח במקום לייצר נתונים שגויים בלוגים.
3. **טלפון ומחשב מבסיס קוד אחד, מימין לשמאל.** כ-PWA האפליקציה ניתנת להתקנה במסך הבית וניגשת למצלמה דרך getUserMedia (בחיבור HTTPS), בלי חנויות אפליקציות. כיווניות מימין לשמאל ממומשת במאפיין dir="rtl" ובמאפייני CSS לוגיים (NFR-10, NFR-11).

**חלופה שנדחתה:** אפליקציה נייטיבית (React Native או Flutter) מחייבת בסיס קוד נפרד למסכי המאמן והפצה דרך חנויות, בלי יתרון פונקציונלי ל-MVP.

### 6.1.2 מנוע ראייה ממוחשבת – MediaPipe בדפדפן

**הסבר.** המנוע משתמש ב-Pose Landmarker מחבילת ‎@mediapipe/tasks-vision‎, במצב VIDEO שבו הפונקציה detectForVideo מעבדת כל פריים חדש. לכל פריים מוחזרות 33 נקודות ציון מנורמלות, 33 נקודות בקואורדינטות תלת-ממדיות במטרים (world landmarks), וציון נראות לכל נקודה ([Google AI Edge](https://developers.google.cn/edge/mediapipe/solutions/vision/pose_landmarker/web_js)). מאחר שהקריאה חוסמת את ה-thread הראשי, המנוע – כולל חישוב הזוויות, מכונת המצבים ובדיקת הכללים (סעיף 4.6) – רץ ב-Web Worker. כללי הטכניקה נטענים מהשרת פעם אחת בתחילת האימון, ובסיום כל סט נשלחת לשרת בקשה אחת עם נתוני הסט, החזרות ואירועי השגיאה.

**נימוקים להרצה בדפדפן ולא בשרת**

1. **פרטיות (NFR-07).** הווידאו אינו יוצא מהמכשיר, ולכן אין צורך להצפין, לאחסן או למחוק צילומי גוף. המידע הרגיש שהמערכת מחזיקה מצטמצם לנתונים מספריים.
2. **השהיה (NFR-01).** עיבוד בשרת מחייב העלאת וידאו רציף והמתנה לתשובה דרך רשת סלולרית שאינה בשליטת המערכת. בעיבוד מקומי ההשהיה תלויה רק בזמן העיבוד במכשיר, והמשוב ממשיך לעבוד גם בניתוק מהרשת (NFR-12).
3. **עלות ויכולת גידול.** כל מכשיר מעבד את הווידאו שלו, והשרת מקבל בקשה קטנה אחת לכל סט. כך אין צורך בשרתי GPU, ועומס השרת גדל לפי מספר הסטים ולא לפי שעות הווידאו.

**סיכון ומענה:** בטלפונים חלשים קצב העיבוד עלול לרדת מתחת ל-15 פריימים לשנייה (NFR-02). במקרה זה המערכת עוברת לגרסת המודל הקלה ביותר, והסיכון מפורט בפרק 8. השוואת ספריות הערכת התנוחה מופיעה בסעיף 2.2.

**כיווני צילום ב-MVP:** סקוואט ולחיצת כתפיים – חזית; לאנג'ים וכפיפת מרפקים – צד. הכיוון נשמר ב-Exercises.camera\_view, ומסך ההכנה (מסך 2) מנחה את המתאמן לפיו.

### 6.1.3 צד שרת – Python, FastAPI ו-Pydantic

**הסבר.** שרת REST אסינכרוני שרץ על Uvicorn (ASGI). גישה למסד הנתונים מתבצעת דרך SQLAlchemy 2.0 עם מנהל ההתקשרות ODBC של SQL Server, ושינויי סכמה מנוהלים כקבצי הגירה ב-Alembic. מנוע ההתראות (BR-06 עד BR-08) רץ כמשימה מתוזמנת יומית ב-APScheduler, והסיסמאות נשמרות כ-hash באלגוריתם Argon2.

**נימוקים לבחירה**

1. **אימות נתונים בכניסה.** כל בקשה מאומתת מול מודל Pydantic מוצהר, כולל טווחי ערכים (זווית בין 0° ל-180°, ציון בין 0 ל-100), לפני שהיא מגיעה למסד הנתונים. כך נשמרת איכות הלוגים שמהם נבנים הדוחות.
2. **תיעוד API שנוצר מהקוד.** FastAPI מפיק מסמך OpenAPI ומסכי Swagger UI ו-ReDoc באופן אוטומטי ([FastAPI](https://fastapi.tiangolo.com/features/)). החוזה בין הלקוח לשרת תמיד מעודכן, וממנו נוצרים טיפוסי הלקוח ובדיקות ה-API.
3. **אכיפת הרשאות בנקודה אחת.** מנגנון ה-Dependency Injection מאפשר לממש את בדיקת התפקיד והשיוך הפעיל (סעיף 4.5) כתלות אחת שמוצמדת לכל נקודת קצה, על בסיס תמיכה מובנית ב-OAuth2 ו-JWT (NFR-06). הריצה האסינכרונית מאפשרת לשרת להמשיך לענות לבקשות בזמן הפקת דוח (NFR-04).

**חלופה שנדחתה:** Node.js עם Express מתאים טכנית, אך Python נבחרה בזכות ספריות עיבוד הנתונים והדוחות. בנוסף, אותה שפה משמשת את ניתוח בדיקות הדיוק בפרק 9.

### 6.1.4 מסד נתונים – SQL Server 2022

**הסבר.** מסד נתונים רלציוני עם 17 טבלאות מנורמלות (סעיף 4.3). בפיתוח ובפיילוט המערכת תשתמש במהדורת Express החינמית, שמוגבלת ל-10GB למסד נתונים, ל-4 ליבות ול-1,410MB זיכרון מטמון ([Microsoft Learn](https://learn.microsoft.com/sql/sql-server/editions-and-components-of-sql-server-2022)). לפי הערכה שלנו, 50 מתאמנים שמתאמנים 3 פעמים בשבוע ייצרו כ-1.6 מיליון שורות חזרה ושגיאה בשנה, פחות מ-1GB כולל אינדקסים. המגבלה אינה חסם בשנה הראשונה.

**נימוקים לבחירה ב-RDBMS ולא ב-NoSQL**

1. **הנתונים רלציוניים מטבעם.** ההיררכיה אימון ← סט ← חזרה ← שגיאה, והשיוך בין מאמן למתאמן לאורך זמן, מוגנים במפתחות זרים ובאילוצים: UNIQUE על דוח לכל אימון, ו-CHECK על טווחי ציון וסטטוס. כך חלק מהכללים העסקיים נאכף במסד עצמו, ולא רק בקוד.
2. **טרנזקציות ACID.** סגירת סט כותבת לשלוש טבלאות (ExerciseSets, Repetitions, FormErrorEvents) ומעדכנת את ציון האימון ביחידה אחת. כשל באמצע אינו משאיר סט חלקי שיעוות את הדוח.
3. **שאילתות אנליטיות ועברית.** הדוחות והדשבורד שואלים על פני אימונים, מתאמנים ומאמנים: ממוצע 3 אימונים קודמים (BR-04) ואחוז החזרות עם שגיאה (BR-05). אלה שאילתות JOIN ו-Window Functions על עמודות מאונדקסות. עברית נשמרת ב-NVARCHAR עם Collation עברי (Hebrew\_CI\_AS), והשדה summary\_json נתמך בפונקציות JSON גם במהדורת Express.

**חלופה שנדחתה:** ב-MongoDB מסמך מקונן מתאים לאימון בודד. אבל רוב השאילתות במערכת נמתחות על פני כמה אימונים וכמה משתמשים, ושלמות השיוך היא תנאי לאבטחת המידע. במקרים אלה מודל רלציוני מתאים יותר.

### 6.1.5 מנוע הפקת דוחות – HTML ל-PDF, ו-Excel

**הסבר.** הדוח נבנה מתבנית HTML ב-Jinja2 עם dir="rtl" וגרפי SVG. קובץ ה-PDF מופק מהתבנית בדפדפן Chromium ללא ממשק, המופעל דרך Playwright. קובץ ה-Excel מופק ב-openpyxl, עם גיליון לכל תרגיל ותצוגת גיליון מימין לשמאל (המאפיין rightToLeft של SheetView). ייצוא JSON נוצר ישירות ממודלי Pydantic. ההפקה רצה כמשימת רקע מול מופע Chromium קבוע, כדי לחסוך זמן עלייה בכל דוח (NFR-03).

**נימוקים לבחירה**

1. **תמיכה מלאה בעברית.** מנוע העימוד של Chromium מיישם את אלגוריתם הכיווניות של Unicode, ולכן עברית המשולבת במספרים ובמונחים באנגלית מוצגת נכון. בתיעוד של WeasyPrint טקסט מימין לשמאל מופיע כלא נתמך ([WeasyPrint 53.4](https://doc.courtbouillon.org/weasyprint/v53.4/api_reference.html)), וב-ReportLab נדרש עיבוד נוסף של כיווניות הטקסט. לכן שתי הספריות נדחו.
2. **תבנית אחת למסך ולקובץ.** אותה תבנית HTML ו-CSS משמשת את מסך 5 ואת קובץ ה-PDF. מה שהמאמן רואה הוא מה שנשלח למתאמן, ועיצוב מתוחזק במקום אחד.
3. **Excel שניתן לעבוד איתו.** openpyxl כותב קובץ xlsx מקורי שבו הערכים המספריים נשמרים כמספרים ולא כטקסט, והגיליון מוצג מימין לשמאל ([openpyxl](https://openpyxl.pages.heptapod.net/openpyxl/api/openpyxl.worksheet.views.html)). המאמן יכול למיין, לסנן ולחשב את הנתונים בעצמו (US-14).

**מחיר הבחירה:** Chromium מוסיף לשרת תלות כבדה וצריכת זיכרון. זמן ההפקה בפועל יימדד מול היעד של 10 שניות בבדיקות הביצועים (פרק 9).

## 6.2 סביבת פיתוח, כלי ניהול ובקרת תצורה

הצוות עובד במאגר קוד אחד, עם שלושה רכיבים: לקוח, שרת והגירות מסד נתונים. כל שינוי קוד מקושר ל-User Story, עובר סקירה ובדיקות אוטומטיות, ורק אז נכנס לענף הפיתוח. זה תואם את דרישת נוהל הפרויקטים של החוג לנהל את דרישות הלקוח כ-User Stories במערכת ניהול הפרויקט.
